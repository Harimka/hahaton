# Git Workflow & Регламент синхронизации с GitHub и GitLab

> **Назначение скилла:** Предотвратить повторение типичных ошибок среды Windows и изолированной песочницы (Sandbox) при коммитах и пушах в репозитории проекта Team-04.

## 2. Почему возникали ошибки и как их избегать (Windows & Sandbox Rules)

Любой агент обязан учитывать 4 особенности среды:

### Правило 1: Доступ к сети и песочница (Sandbox)
* **Причина ошибок:** В стандартном режиме песочницы (`BypassSandbox: false`) сеть **полностью отключена**, а создание системных скрытых папок (`.git`) блокируется политиками Windows.
* **Правило:** Любые команды Git, требующие обращения к сети (`git push`, `git fetch`, `git clone`) или модификации `.git`, **ОБЯЗАТЕЛЬНО** выполняются с флагом `BypassSandbox: true`.

### Правило 2: Окончания строк (CRLF vs LF)
* **Причина ошибок:** На Windows при чекауте файлы ST HAL и CMSIS (более 60 файлов) автоматически помечаются как измененные из-за разницы переводов строк (`\r\n` против `\n`).
* **Правило:** В репозитории всегда должно быть выставлено:
  ```powershell
  git config core.autocrlf true
  ```
  Не коммитить служебные изменения переносов строк в папках `Drivers/CMSIS` и `Drivers/STM32G4xx_HAL_Driver`!

### Правило 3: Кириллические имена файлов
* **Причина ошибок:** По умолчанию Git экранирует русские буквы в названиях файлов восьмеричными кодами (`\320\232...`), что приводит к ложным удалением и дублям.
* **Правило:** Всегда держать активным:
  ```powershell
  git config core.quotepath false
  ```

## 3. Стандартный алгоритм коммита и пуша (SOP)

Когда агент завершил задачу и готов зафиксировать изменения:

### Шаг 1: Проверка статуса (без лишних файлов)
```powershell
git status --short
```
Убедиться, что в списке нет временных файлов сборки (`.elf`, `.bin`, `build/CMakeCache.txt`). Папка `firmware/build/` должна игнорироваться через `.gitignore`.

### Шаг 2: Добавление изменений
Никогда не использовать слепой `git add .`, если изменены чужие системные файлы HAL.
```powershell
# Для конкретных файлов задачи:
git add docs/ firmare/App/ scripts/
# Либо полный add, если статус чистый:
git add -A
```

### Шаг 3: Сообщение коммита (Conventional Commits)
Сообщение пишется на английском языке в формате: `<тип>: <краткое описание>`.
Типы:
* `feat:` — новая функциональность (например, `feat: add onboard smallwood srs calculation`);
* `fix:` — исправление ошибки или бага;
* `docs:` — обновление документации или ТЗ;
* `refactor:` — рефакторинг кода без изменения логики;
* `chore:` — технические изменения скриптов или gitignore.

Пример команды:
```powershell
git commit -m "feat(srs): implement smallwood ramp-invariant filter on Cortex-M4 FPU"
```

### Шаг 4: Пуш в GitHub (`origin`)
```powershell
git push origin developV2
```

### Шаг 5: Синхронизация с судейским GitLab (`gitlab`)
Перед тестовыми прогонами на стенде или сдачей этапа код зеркалируется в GitLab:
```powershell
# Пуш рабочей ветки developV2 в целевую ветку main репозитория GitLab:
git push gitlab developV2:main
```

## 4. Чек-лист перед вызовом `git push`
1. [ ] Установлен параметр `BypassSandbox: true`.
2. [ ] В коммит не попали файлы из `build/` или временные логи.
3. [ ] Проект компилируется локально без ошибок (`build.bat` завершается кодом 0).
4. [ ] В коде нет запрещенных упоминаний чужих библиотек или заглушек.
