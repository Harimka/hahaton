## 1. Контракт блока отсчёта датчика (в ОЗУ прошивки)

Используется для передачи данных из прерывания / DMA драйвера акселерометра в кольцевой буфер и FSM.

```cpp
#pragma pack(push, 1)
struct ImuRawSample {
    uint32_t timestampUs;   ///< Время отсчета в микросекундах от старта таймера
    uint32_t sampleIndex;   ///< Сквозной счетчик отсчетов (для детекции пропусков)
    int16_t  rawX;          ///< Сырое значение X (чувствительность 0.488 mg/LSB при ±16g)
    int16_t  rawY;          ///< Сырое значение Y
    int16_t  rawZ;          ///< Сырое значение Z
    uint8_t  flags;         ///< Битовые флаги:
                            ///< Bit 0: Overrun / FIFO overflow
                            ///< Bit 1: Saturation (достигнут предел ±16g)
                            ///< Bit 2: SPI CRC / Read error
                            ///< Bit 3: Reserved
};
#pragma pack(pop)
```

### Диагностика потерь и ошибок
- **Счетчик `sampleIndex`:** инкрементируется на каждый DRDY/отсчет. Скрипт на ПК проверяет: если `sampleIndex[i+1] != sampleIndex[i] + 1`, фиксируется пропуск пакета.
- **Флаг Overrun (бит 0):** выставляется драйвером, если флаг `XLDA` в `STATUS_REG` не был вычитан вовремя до прихода следующего отсчета.

## 2. Формат бинарного файла сигнала на SD (`raw_signal_XXXX.bin`)

Имя файла: `raw_signal_XXXX.bin`, где `XXXX` — метка времени начала кадра (timestamp в миллисекундах или секундах).

### Структура файла:
```
┌────────────────────────────────────────────────────────┐
│ HEADER (32 байта)                                      │
├────────────────────────────────────────────────────────┤
│ SAMPLES DATA (N × 16 байт)                             │
└────────────────────────────────────────────────────────┘
```

#### Заголовок (File Header — 32 байта, Little-Endian):
```cpp
#pragma pack(push, 1)
struct RawSignalFileHeader {
    char     magic[4];          ///< "SHK1" (Shock Format v1)
    uint16_t version;           ///< 0x0001
    uint16_t headerSize;        ///< 32 байта
    float    sampleRateHz;      ///< 6660.0f
    float    scaleFactorG;      ///< 0.000488f (коэффициент перевода raw в g)
    uint32_t eventId;           ///< Порядковый номер зарегистрированного удара
    uint32_t sampleCount;       ///< Количество сэмплов в данном файле
    uint32_t triggerTimestamp;  ///< Время срабатывания триггера >3g (us)
    uint32_t reserved;          ///< Выравнивание до 32 байт (0x00)
};
#pragma pack(pop)
```

#### Тело файла (Запись одного отсчёта — 16 байт):
```cpp
#pragma pack(push, 1)
struct RawSignalRecord {
    uint32_t timestampUs;   ///< Время отсчета в микросекундах
    float    ax;            ///< Ускорение по оси X [g] (компенсированное)
    float    ay;            ///< Ускорение по оси Y [g] (компенсированное)
    float    az;            ///< Ускорение по оси Z [g] (компенсированное)
};
#pragma pack(pop)
```
*Требование ТЗ:* Скрипт парсинга преобразует эти записи в CSV со столбцами `[t, ax, ay, az]`.

## 3. Формат бинарного файла спектра SRS (`raw_srs_XXXX.bin`)

Имя файла: `raw_srs_XXXX.bin` (метка времени `XXXX` строго совпадает с исходным `raw_signal_XXXX.bin`).

### Структура файла:
```cpp
#pragma pack(push, 1)
struct RawSrsFileHeader {
    char     magic[4];          ///< "SRS1" (SRS Format v1)
    uint16_t version;           ///< 0x0001
    uint16_t numPoints;         ///< 94 (число точек частотной сетки)
    float    qFactor;           ///< 10.0f (добротность осцилляторов)
    uint32_t eventId;           ///< ID соответствующего удара
    uint32_t reserved[4];       ///< Выравнивание заголовка
};

struct RawSrsPoint {
    float fn;   ///< Собственная частота осциллятора [Гц] (по сетке)
    float gx;   ///< Maximax спектральный отклик по оси X [g]
    float gy;   ///< Maximax спектральный отклик по оси Y [g]
    float gz;   ///< Maximax спектральный отклик по оси Z [g]
};
#pragma pack(pop)
```
*Требование ТЗ:* Скрипт парсинга преобразует файл в CSV со столбцами `[f, gx, gy, gz]`.

## 4. Алгоритм компенсации гравитации и калибровки
* **Где компенсируется:** В слое бизнес-логики (`TriggerFsm` в `firmware/App/`), а НЕ внутри драйвера LSM6DS3! Драйвер всегда отдает честные сырые данные.
* **Как компенсируется:**
  1. В состоянии `IDLE` (до удара) прошивка накапливает скользящее среднее (Baseline) по окну в 200–500 мс для каждой оси: $\overline{a_x}, \overline{a_y}, \overline{a_z}$. В состоянии покоя на вертикальной оси $Z$ будет $\approx 1.0g$, а на горизонтальных $\approx 0.0g$.
  2. Значение ускорения удара вычисляется как:
     $$a_{dyn}(t) = a(t) - \overline{a}_{static}$$
  3. Триггер срабатывает при условии:
     $$\max(|a_{x, dyn}|, |a_{y, dyn}|, |a_{z, dyn}|) \ge 3.0g$$

## 5. Выделение кадра удара ($0.25 \cdot A_{\max}$)
* В кольцевой буфер непрерывно пишутся сэмплы (предыстория $\ge 200$ мс).
* При триггере фиксируется удар до момента затухания колебаний.
* Находится $A_{\max} = \max_{t} |a(t)|$ по оси удара.
* Вычисляется уровень отсечки: $A_{cut} = 0.25 \cdot A_{\max}$.
* **Границы кадра:**
  - Начало: первый отсчет перед пиком, где $|a(t)| \ge A_{cut}$ (плюс запас в 10–20 сэмплов предыстории для сохранения переднего фронта).
  - Конец: последний отсчет после затухания, где $|a(t)| \ge A_{cut}$.
